# SRE — 운영 성숙도 순차 진단

프로젝트가 **돌아가는 시스템을 지킬 수 있는 상태인가**를 저장소 정적 분석으로 판정하고, 누락 항목과 개선 경로를 제시한다.

계보는 Google SRE의 **Production Readiness Review** — 서비스를 운영으로 넘기기 전에 신뢰성 요건 충족을 확인하는 절차다. PRR이 다루는 영역과 이 스킬의 축 대응:

| PRR 영역 | 이 스킬 |
|----------|---------|
| 계측·메트릭·모니터링 | L1 · L2 |
| 긴급 대응 | L3 · L5 |
| 변경 관리 | L4 |
| 용량 계획 | L6 |
| 성능(가용성·지연·효율) | L3의 SLI/SLO로 다룬다 — 성능 자체를 독립 축으로 두지 않는 것은 정적 분석으로 실측이 불가능하기 때문이다 |
| 시스템 아키텍처·의존 구조 | 이 스킬 범위 밖 → `harness-engineering`의 `resources/06-arch-test-tools.md` |

## Core Principles

1. **저장소만 본다** — 코드·설정 파일과 **git 이력**으로 판정한다. 런타임 실측(SSH·대시보드 쿼리·엔드포인트 호출)은 이 스킬의 범위가 아니다. 파일로 확인 불가한 항목은 판정하지 않고 **"확인 필요"**로 표시한다
2. **없는 것을 찾는다** — 코드 리뷰는 있는 코드의 결함을 보지만, 이 스킬은 **있어야 하는데 없는 것**을 본다. 검사 대상 파일이 존재하지 않는다는 사실 자체가 발견이다
3. **소유한 영역은 제안까지, 남의 영역은 발견만** — 이 스킬이 소유한 다섯 영역(관측성·알림/SLO·배포안전성·운영준비도·용량비용)은 개선 방법까지 제시한다. 그 밖의 영역은 발견 사실만 적고 담당 스킬로 넘기며, **탐지 절차든 수정 절차든 복제하지 않는다** (아래 위임 경계표)
4. **근거를 남긴다** — 각 지적에 `파일:라인` 또는 "부재 확인 경로"를 함께 제시한다. "없음"도 어디를 봤는지 밝힌다
5. **순차 진행** — 앞 축의 결과가 뒤 축의 검사 항목을 결정한다. 건너뛰면 무의미한 항목을 검사하게 된다

## 스캔 제외 경로 (전 축 공통)

모든 Glob·Grep에 아래 제외를 적용한다. 빠뜨리면 카운트가 부풀려져 판정이 뒤집힌다.

```
node_modules  .next  .nuxt  dist  build  out  target  vendor  coverage
.git  .venv  __pycache__  *.min.*  *.map
.claude/worktrees        ← 저장소 사본이 통째로 들어 있어 모든 카운트가 중복된다
```

**중첩 경로는 `!**/{경로}/**` 형태로 써야 실제로 제외된다.** 실측: `-g '!.claude/worktrees'` → 3건(제외 안 됨) / `-g '!**/.claude/worktrees/**'` → 1건.

제외 인자는 반드시 **따옴표로 감싼다** — 변수에 담아 비인용 확장하면 셸이 `!`·`*`를 먼저 먹어 인자가 망가지고, 결과가 조용히 0건이 된다.

```
rg -l '패턴' \
  -g '!**/node_modules/**' -g '!**/.next/**' -g '!**/.nuxt/**' \
  -g '!**/dist/**' -g '!**/build/**' -g '!**/out/**' -g '!**/target/**' \
  -g '!**/vendor/**' -g '!**/coverage/**' -g '!**/.venv/**' \
  -g '!**/__pycache__/**' -g '!**/.claude/worktrees/**' \
  -g '!*.min.*' -g '!*.map' -g '!*.lock'
```

테스트 픽스처·예제 파일(`**/test/**`, `**/__tests__/**`, `*.test.*`, `*.spec.*`, `.env.example`)은 **항목에 따라** 제외한다 — `console.log`·시크릿 후보 카운트에서는 빼고, 런북·설정 존재 확인에서는 넣는다.

## 정규식 함정 (실측 확인됨)

| 함정 | 실측 | 대응 |
|------|------|------|
| **약어에 `\b`를 걸면 한국어 문서를 놓친다** | `\bSLO\b`는 `SLO를`·`SLO는`에 **매칭 안 됨**(한글 음절이 word character) | `\b` 대신 **대소문자 구분**을 쓴다. `--case-sensitive 'SLO'`는 `SLO를`을 잡고 `isLoading`·`slot`·`slow`·`AccessLogFilter`는 걸리지 않는다 (실측 7건 → 3건, 오탐 0) |
| **`\b`는 스네이크/카멜 내부에 없다** | `\b(cpu\|memory)\b` → `container_memory_usage_bytes`에 **0건**. `\bErrorRate\b` → `HighErrorRate`에 **0건** | 메트릭·알림 이름은 경계 없이 부분 문자열로 찾는다 |
| **여러 줄에 걸친 패턴은 기본 모드에서 항상 0건** | rg는 라인 단위 매칭이라 `[\s\S]{0,N}`이 개행을 못 넘는다 | 멀티라인 패턴에는 **`-U`(`--multiline`)** 를 반드시 붙인다 |
| **부정 전방탐색은 명령이 죽는다** | `(?!...)` → `regex parse error` 로 중단 | `--pcre2`를 쓰거나, "A는 있고 B는 없다"를 **두 번의 검색과 집합 연산**으로 나눈다 |

| **존재 확인 grep의 히트는 그 자체로 증거가 아니다** | `Grep "restore"`는 `actions/cache`의 `restore-keys:`에 걸린다. `timeout`은 `testTimeout`·`timeout-minutes`에 걸린다 | 매칭 **위치를 열어** 그 기능의 구현·설정인지 확인한 것만 센다. 확인하지 않은 히트는 PASS 근거가 아니라 `확인 필요`다 |

**0건은 "부재"가 아니라 "미탐일 수도 있음"이다.** 두 방향 모두 위험하다:

- **부재 탐지 패턴이 0건** → 이 스킬은 부재를 발견으로 취급하므로(원칙 2) 곧바로 결함 보고가 된다. 반대 패턴이 1건이라도 잡히는지로 교차 확인한다
- **위반 탐지 패턴이 0건** → "위반 없음"으로 읽혀 **Critical 체크가 조용히 통과한다.** 이쪽이 더 위험하다. 패턴이 멀티라인인지(`-U` 누락), 대소문자·언어 변형을 놓쳤는지 먼저 확인하고, 대상 파일이 실제로 스캔 범위에 있었는지 파일 수로 검산한다

## 등급 산출 규칙 (단일 출처)

축 등급은 그 축에서 **확정된 Check의 최고 심각도**로 정한다. 이것이 등급의 유일한 정의다 — 축별 파일에는 별도 판정표가 없고, `## 판정` 섹션에 **그 축에만 걸리는 예외**(심각도 상·하향, 라벨 적용 조건)만 있다.

| 확정된 최고 심각도 | 축 등급 |
|-------------------|---------|
| Critical 1개 이상 | **FAIL** |
| Critical 0 + High 1개 이상 | **WARN** |
| Critical 0 + High 0 (Medium만 또는 없음) | **PASS** — Medium은 리포트에 남기되 등급을 내리지 않는다 |

"확정"이 아닌 것은 등급에 반영하지 않는다:

| 라벨 | 범위 | 등급 반영 |
|------|------|----------|
| **확인 필요** | 개별 항목이 저장소만으로 판정 불가 (실제 사용량·복구 성공 여부 등) | 그 항목만 제외. 축은 나머지로 정상 판정 |
| **판정 보류** | 축의 검사 항목 **과반**이 저장소 밖이거나, 확정된 Check가 0개인데 확인 필요가 과반 | 축에 등급을 매기지 않음 |
| **선행 조건 미충족** | 토대가 없어 판정이 무의미 (L3에 수집 경로 없음) | 축에 등급을 매기지 않음 |

| **해당 없음** | 그 저장소에 검사 대상 자체가 존재하지 않음 (라이브러리에 HTTP 에러 표면, 상태 없는 서비스에 백업) | **분모에서 제외.** `확인 필요`와 다르다 — 모르는 게 아니라 없는 것이다 |

**확정된 Check가 1개라도 있으면 축은 그 최고 심각도로 등급을 받는다.** `판정 보류`는 **확정 Check가 0개일 때만** 축 단위로 적용한다. 그 외에는 저장소 밖 항목을 `확인 필요`로 빼고 나머지로 판정한다 — 확정된 Critical이 라벨에 삼켜져 집계에서 사라지면 안 된다.

**"확정 0개"를 PASS로 읽지도 않는다.** 아무 결함도 못 찾은 것과 아무것도 확인하지 못한 것은 다르다. 확정 Check가 0개면 "그 축의 검사 항목(`해당 없음` 제외) 중 몇 개를 실제로 확인했는가"를 세고, 과반을 못 봤으면 `판정 보류`다.

### 심각도 기준선 — Phase 1 시작 전에 확정한다

Check 심각도가 곧 등급이므로, **운영 성격에 따른 조정은 축을 판정하기 전에 정해야 한다.** 판정한 뒤에 조정하면 6축을 전부 재계산해야 하고, 실제로는 재계산되지 않는다.

인벤토리(Phase 0)에서 파악한 성격으로 기준선을 정하고, 정한 내용을 리포트에 적는다.

| 성격 | 조정 |
|------|------|
| 개인 프로젝트·내부 도구 | on-call·postmortem·무중단 배포·런북 관련 Check를 **1단계 하향**. 부재 자체를 결함으로 보지 않음 |
| 외부 사용자 대상 서비스 | 기본 심각도 유지 |
| 금융·규제 대상 | 백업·감사 로그·시크릿 관리를 **1단계 상향**. 규제 요건 자체는 `/security` 위임 |
| PoC·데모 | L1·L4에 집중. L3·L5·L6의 Check를 **1단계 하향**(축을 빼지는 않는다 — 등급은 매기되 낮게 나올 뿐) |

조정 없이 같은 기준을 모든 프로젝트에 적용하면 개인 프로젝트가 전부 FAIL로 나와 리포트가 무시된다. **이 표가 심각도 조정의 유일한 정의다** — 축별 파일에 중복해서 적지 않는다.

## 인자 해석

| 인자 | 동작 |
|------|------|
| 없음 | 현재 저장소 전체, L0~L6 전 축 |
| 축 이름 (`logging,alerting`) | 해당 축만. L0 인벤토리는 항상 선행 실행 |
| 경로 | 해당 경로를 루트로 간주하여 전 축 |

축 이름: `inventory` `logging` `metrics` `alerting` `deploy` `operability` `capacity`

## Workflow

```
Phase 0  인벤토리          resources/00-inventory.md
Phase 1  축별 순차 진단     resources/01~06 (L0 결과로 항목 선별)
Phase 2  통합 리포트        resources/07-report-template.md
Phase 3  후속 제안          위임 라우팅
```

### Phase 0: 인벤토리

`resources/00-inventory.md`를 로드하여 스택·런타임·오케스트레이션·관측 스택·배포 경로를 감지한다.

이 결과가 **이후 모든 축의 검사 항목을 고른다**. 예: compose가 없으면 L4의 compose healthcheck 항목은 검사 대상에서 빠지고, 대신 "배포 단위가 무엇인지 확인 필요"가 된다.

인벤토리 결과를 먼저 사용자에게 1개 표로 보여주고 진행한다 — 감지가 틀렸으면 이후 판정이 전부 틀리므로 여기서 교정받는다.

### Phase 1: 축별 순차 진단

| 순서 | 축 | 리소스 | 선행 조건 |
|------|-----|--------|-----------|
| L1 | 로깅 | `01-logging.md` | — |
| L2 | 메트릭·트레이싱 | `02-metrics-tracing.md` | — |
| L3 | 알림·SLO | `03-alerting-slo.md` | L1 또는 L2 중 하나가 최소 수집 경로를 가짐 |
| L4 | 배포 안전성 | `04-deploy-safety.md` | — |
| L5 | 운영 준비도 | `05-operability.md` | — (에러 표면 항목은 L1의 상관 ID와 교차 확인) |
| L6 | 용량·비용 | `06-capacity-cost.md` | — (**관측 보존 항목만** L1·L2 결과에 의존. 리소스 제한·로그 회전은 항상 판정) |

관측 스택이 OpenTelemetry면 L1·L2·L6에서 `08-otel-conventions.md`를 함께 로드한다 — 계측 여부가 아니라 **규약대로 썼는지**를 보는 항목들이 거기 있다. 이 파일은 독립 축이 아니라 세 축의 판정에 합류한다.

각 축에서:

1. 해당 리소스를 Read
2. Detection Patterns / Grep Patterns으로 스캔 — **파일 부재도 결과로 기록**. 0건이면 패턴이 동작했는지 교차 확인
3. 확정된 Check를 Critical/High/Medium으로 분류하고, 판정 불가 항목은 `확인 필요`로 뺀다
4. **등급 산출 규칙**(위)으로 축 등급 결정. 축별 파일의 `## 판정` 섹션에 있는 예외를 먼저 적용한 뒤 계산한다

**선행 조건 미충족 처리**: L3는 로그도 메트릭도 수집 경로가 없으면 알림을 걸 대상이 없다. 이때 L3를 FAIL로 판정하지 않고 **"선행 조건 미충족 — L1/L2 해결 후 재평가"**로 표시한다. 없는 토대 위에서 내린 판정은 노이즈다.

### Phase 2: 통합 리포트

`resources/07-report-template.md`의 형식을 따른다. 세션에는 요약, 상세는 vault 페이지.

**종합 Verdict 집계**:

| 조건 | 판정 |
|------|------|
| 축 중 FAIL 1개 이상 | **FAIL** |
| FAIL 0 + WARN 3개 이상 | **WARN** |
| 그 외 | **PASS** |

**집계에서 제외하는 축**: 등급이 없는 축 — `판정 보류`·`선행 조건 미충족`. 리포트에 사유와 함께 별도 표시한다 — **판정하지 않은 축이 조용히 PASS에 기여하면 안 된다.**

등급이 매겨진 축이 **절반 미만(3개 미만)이면 종합 Verdict를 내지 않고 "부분 판정"으로 보고한다** — 6축 중 1축만 보고 시스템 전체를 PASS/FAIL로 부르지 않는다. 전 축이 등급 없음이면 "이 저장소만으로는 판정 불가"다.

### Phase 3: 후속 제안

발견 항목마다 담당 스킬을 붙여 다음 행동을 제시한다. 우선순위는 **Critical → 선행 조건을 푸는 항목 → High** 순.

선행 조건을 푸는 항목을 High보다 앞에 두는 이유: L1 수집 경로를 만들면 L3·L6의 판정 자체가 가능해지므로, 같은 노력으로 더 많은 축이 움직인다.

## 위임 경계

이 스킬이 소유하는 것: **관측성 · 알림/SLO · 배포 안전성 · 운영 준비도 · 용량/비용**.

발견은 여기서, 수정은 아래로 넘긴다.

| 발견 | 담당 |
|------|------|
| CI 파이프라인·justfile 부재, 로컬 CI 구성 | `/devops` (ci-cd) |
| 배포 빈도·리드타임 개선 (배치 축소, 파이프라인 단축) | `/devops` (ci-cd) — 지표 산출은 L4가, 처방은 여기 |
| 이미지 크기·멀티스테이지·베이스 이미지 선택 | `/devops` (docker) — L6은 "빌드 도구 잔존" 신호만 남기고 판별은 넘긴다 |
| Dockerfile·compose 구성 개선 | `/devops` (docker) |
| GitHub Actions workflow 작성·수정 | `/devops` (github-action) |
| 시크릿 노출, 취약점, 권한 | `/security` |
| lint·타입·죽은 코드 | `/code-review` |
| Terraform lifecycle·state | `/terraform` |
| 아키텍처 불변식이 강제되지 않음 | `harness-engineering` `resources/06-arch-test-tools.md` |
| 규약이 문서·주석에만 존재 | `/code-review` Workflow 5 |
| 도구 버전·환경변수 관리 | `/mise-config` |

**판단 기준**: "이것을 고치는 방법이 이미 다른 스킬에 있는가?" — 있으면 위임한다. 이 스킬은 **무엇이 없는지**를 찾는 데 집중한다.

## 원칙 연계

| 원칙 | 이 스킬에서의 적용 |
|------|-------------------|
| `EXECUTABLE-DOCUMENTATION` | 런북·SLO가 문서로만 있고 검증되지 않으면 없는 것과 같다 |
| `SELF-TESTING-CODE` | 백업은 복구 검증이 자동 실행될 때만 백업이다 |
| `FAIL-FAST` | 헬스체크·타임아웃이 없으면 실패가 늦게 드러난다 |
| `IDEMPOTENCY` | 배포·마이그레이션의 재실행 안전성 |
| `SSoT` | 같은 로그를 두 경로로 수집하면 한쪽이 조용히 버려진다 |

원칙 상세는 `/principles check <NAME>`.

## Examples

### 예시 1: 전체 진단

**User**: `/sre`

1. Phase 0 — compose.yaml + Kotlin/Spring + otel collector 감지 → 인벤토리 표 제시
2. L1 로깅 — logback 구조화 O, MDC 전파 O, 수집 경로 2중(agent + 사이드카) → **WARN**
3. L2 메트릭 — micrometer O, `/actuator/prometheus` 노출 O, 트레이스 전파 O → **PASS**
4. L3 알림 — alert 규칙 파일 0건, SLO 문서 0건 → **FAIL**
5. L4~L6 진행
6. 종합 FAIL, 다음 단계: 알림 규칙부터

### 예시 2: 축 지정

**User**: `/sre logging,alerting`

→ Phase 0(항상) → L1, L3만 진단 → 리포트에 미검사 축 명시

### 예시 3: 없는 것이 발견인 경우

**User**: `/sre` (Next.js 프로젝트)

→ `console.log` 47건, 로깅 라이브러리 의존성 0건, 수집 경로 설정 없음
→ L1 **FAIL** — "로그가 stdout으로만 나가고 수집되지 않음. 배포 후 로그를 볼 방법이 없음"
→ L3는 선행 조건 미충족으로 미판정

## Anti-Patterns

| 문제 | 해결 |
|------|------|
| 인벤토리 없이 축부터 검사 | 무관한 항목을 지적하게 됨. Phase 0 먼저 |
| 파일이 없으면 검사를 건너뜀 | 부재가 곧 발견이다. "없음"을 결과로 기록 |
| 다른 스킬의 체크리스트를 복제 | 위임 경계표대로 넘긴다 |
| 런타임을 추측해서 판정 | 파일로 확인 불가하면 "확인 필요" |
| 모든 축을 FAIL로 채움 | 선행 조건 미충족 축은 판정 보류 |
