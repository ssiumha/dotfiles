# 리포트 형식

세션에는 **요약**, vault에는 **상세**. 같은 내용을 두 번 쓰지 않는다 — 세션 요약은 판정과 다음 행동만, 근거·패턴·미검사 항목은 페이지에 둔다.

## 세션 출력

```markdown
## SRE Audit — {project} ({YYYY-MM-DD})

### 인벤토리
| 항목 | 감지 결과 |
|------|----------|
| 스택 | ... |
| 애플리케이션 서비스 수 | 1 (앱 1 + postgres·redis는 기성 컨테이너) |
| 배포 단위 | ... |
| 관측 스택 | ... |
| 미감지 | ... |

### 심각도 기준선
운영 성격: {개인 프로젝트 / 외부 서비스 / 규제 대상 / PoC} — {적용한 조정}

### 축별 판정
| 축 | 판정 | 근거 (1줄) |
|----|------|-----------|
| L1 로깅 | WARN | 구조화 O, 상관 ID 전파 없음 |
| L2 메트릭·트레이싱 | PASS | micrometer + OTLP, Golden Signals 4개 O |
| L3 알림·SLO | FAIL | 알림 규칙 0건 |
| L4 배포 안전성 | 판정 보류 | 배포 설정이 인프라 저장소 — 확정 Check 0개 |
| L5 운영 준비도 | FAIL | 백업 스크립트 O, 복구 절차 없음 |
| L6 용량·비용 | WARN | 로그 회전 O, 보존 정책 없음 |

등급이 없는 축(`판정 보류`·`선행 조건 미충족`)은 사유와 함께 표에 남기고 집계에서 뺀다.

### 종합 Verdict: FAIL (집계 대상 5축)

### 누락 항목 (심각도순)
**[Critical]** `scripts/backup.sh` — 백업만 있고 복구 절차·검증 없음 → 복구를 CI 잡으로 (`/devops` ci-cd)
**[Critical]** 알림 규칙 부재 (`**/alert*.y*ml` 0건) — 장애를 사용자가 먼저 알게 됨 → 증상 3개부터
**[High]** `src/lib/logger.ts:12` — 상관 ID 미전파 → traceparent 바인딩

### 다음 단계
1. [우선] 알림 규칙 3개 (가용성·에러율·p95) — L3 FAIL 해소
2. [우선] 복구 검증 잡 — 백업이 백업이 되게
3. [중간] 상관 ID 전파 — L5 에러 표면과 함께 처리하면 한 번에 끝남

상세: [[{YYYY-MM-DD}-sre-audit]]
```

**축이 5개 이상 WARN/FAIL이어도 "다음 단계"는 3개를 넘기지 않는다.** 전부 나열하면 아무것도 시작되지 않는다. 선행 조건을 푸는 항목을 우선한다.

## vault 페이지

**개인 지식 저장소는 환경마다 있고 없고가 다르다. 있을 때만 쓴다.**

| 상황 | 상세 리포트 위치 |
|------|-----------------|
| `documentation` 스킬이 있고 vault 경로가 실재 | `projects/{name}/investigation/{YYYY-MM-DD}-sre-audit.md` |
| 없음 | **세션 출력에 상세까지 포함**하고 파일을 만들지 않는다. 대상 저장소에 쓰지 않는다 — 개인 도구 산출물을 팀 저장소에 남기지 않는다 |

vault를 쓰는 경우에만 아래를 따른다. 위치·namespace 판단은 `documentation` 스킬, 형식 규약은 `obsidian-write` 스킬. **두 스킬에 없는 경로·키를 임의로 만들지 않는다.**

- `investigation/`은 `documentation` 스킬 기준 **`projects/{name}/` 하위에만** 존재한다. 대상이 vault 프로젝트가 아니면 새 루트 네임스페이스를 만들지 말고, `documentation`의 매핑 표를 먼저 갱신할지 사용자에게 확인한다
- `obsidian-write`는 **`type`을 별도 frontmatter key로 두지 않는다** — 폴더가 이미 구분한다. `tags`·`related`도 그 스킬의 규약에 없다

```markdown
---
project: pj-{name}
date: {YYYY-MM-DD}
status: open
last-verified: {YYYY-MM-DD}
---

# SRE Audit — {project} {YYYY-MM-DD}

## 인벤토리
{감지 표 + 미감지 항목}

## 축별 판정
{세션과 동일한 표}

## 축별 상세

### L1 로깅 — WARN
- 확인한 것: {검사 경로·패턴}
- 발견: {파일:라인 근거}
- 확인 필요: {정적 분석으로 판정 불가한 항목}

{L2~L6 동일}

## 미검사 / 판정 보류
| 항목 | 사유 |
|------|------|
| L4 배포 안전성 일부 | 배포 설정이 저장소 외부 |
| 실제 카디널리티 | 런타임 실측 필요 |

## 다음 단계
- [ ] {항목} → {담당 스킬}
```

**`## 미검사 / 판정 보류`를 비워두지 않는다.** 정적 분석의 한계를 명시해야 이 리포트를 나중에 읽는 사람이 "다 봤다"고 오해하지 않는다.

## 저널 연결

namespace 페이지를 만들면 당일 저널에 링크를 남긴다 (`obsidian-write` 연결 원칙).

```
- [x] {project} SRE 진단 — 종합 FAIL, 알림·복구 검증 부재 #pj-{name}
    -> [[{YYYY-MM-DD}-sre-audit]]
```

## 재실행 시

같은 프로젝트에 이전 감사 페이지가 있으면 (`ir search` 또는 Glob `**/*sre-audit*`) **대조 섹션을 추가**한다.

```markdown
## 이전 대비 ({이전 날짜} → {오늘})

| 축 | 이전 | 현재 | 변화 |
|----|------|------|------|
| L3 알림·SLO | FAIL | WARN | 알림 규칙 3개 추가, SLO 미정의 |
| L5 운영 준비도 | FAIL | FAIL | 변화 없음 |

**해소**: {항목}
**신규**: {항목}
**미해결 (2회 연속)**: {항목} ← 우선 처리 대상
```

이전 페이지의 `status`를 `open` → `resolved`로 바꾸지 않는다. 감사 기록은 시점 스냅샷이므로 각각 남긴다. 대신 **이전 페이지 본문 하단에 `-> [[{새 페이지}]]` 링크를 추가한다** (`obsidian-write`의 연결 방식 — `related` frontmatter 키는 그 스킬 규약에 없다).

**2회 연속 미해결 항목을 별도로 표시하는 이유**: 매번 같은 지적이 반복되면 그 항목은 실행 불가능한 제안이거나 우선순위가 실제로 낮은 것이다. 세 번째 감사에서도 남아 있으면 제안 자체를 재검토하도록 리포트에 적는다.

## 심각도 조정 표기

조정 규칙 자체는 INSTRUCTIONS의 **심각도 기준선**이 단일 정의이고, Phase 1 **시작 전에** 확정된다. 리포트에는 결과만 적는다.

```markdown
### 심각도 기준선
운영 성격: 개인 프로젝트 — on-call·postmortem·무중단 배포 관련 Check를 1단계 하향
```

**조정했다는 사실을 반드시 적는다.** 적지 않으면 같은 저장소를 다음에 다른 기준으로 재평가해도 차이를 설명할 수 없다.
