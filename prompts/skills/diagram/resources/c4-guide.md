# C4 문서 세트 가이드

C4 모델로 인프라/아키텍처 문서 세트를 만들 때의 레벨 시맨틱과 컨벤션. 넘버링 파일 세트(`01_CONTEXT` · `02_CONTAINERS` · `03_COMPONENTS` + 보충)로 구성하고, 각 문서가 파일명·제목만으로 파악되게 한다 (인덱스/README 문서는 만들지 않는다).

## 레벨 시맨틱

| 레벨 | 대상 | 원칙 |
|------|------|------|
| L1 System Context | 사람 + 시스템 블랙박스 | 컨테이너 정보 노출 금지. 액터 케이스 구분용 부제(예: "platform console")까지만 허용 |
| L2 Container | 배포 가능한 단위 (서비스·DB) | 역할 기반 명명 + 기술 부제. 포트·도메인·프로토콜은 엣지 라벨과 표에 |
| L3 Component | 컨테이너 내부 | **유스케이스 단위 시퀀스**로 푸는 것이 실용적 — 유스케이스별 섹션에 시퀀스 + 단계 상세 표 |
| L4 Code | 코드 | 다이어그램 대신 컴포넌트→`파일:심볼` 포인터 표. L3와 같은 문서에 결합 |

## 방향 컨벤션 (기본값)

- **L1 컨텍스트 체인: 가로** (좌→우)
- **L2 컨테이너 체인: 세로**
- **L3 시퀀스: 세로** (시간 위→아래, 라이프라인 세로선)
- 액터가 복수 역할이면 케이스별로 도식을 분리한다 (예: Platform admin / Tenant admin)

## Deployment vs Topology

- **C4 Deployment diagram** = 배포 노드 중첩(리전→VM→런타임) 안에 **L2 컨테이너 인스턴스**를 배치해 "어디서 도는가"를 답하는 그림. 환경(dev/prod)별 1장
- 노드 매핑 없이 배포 단위 간 연결만 그린 것은 **topology** — 파일명·제목을 deployment로 붙이지 않는다. 이름이 내용을 따라가야 한다
- topology는 노드·엣지가 많아지므로 ASCII보다 mermaid flowchart가 맞는 경우가 많다 (architecture-beta는 저밀도 전용 — SKILL.md 함정 참조)

## 명명 원칙

- 역할 기반 이름 + 기술은 부제: `BFF (Next.js route handlers)`
- 실서비스명과 1:1 대응이 자연스러우면 그대로 쓴다 (억지 일반화 금지)
- 게이트웨이 라우팅 분기는 별도 컴포넌트로 그리지 않는다 — 단일 박스 + 나가는 **엣지 라벨**(`wallet route` 등)로. 분기를 박스로 쪼개면 컴포넌트가 아닌 것이 컴포넌트처럼 보인다
- DB 연결 표기는 `host:port/dbname` (접속 URL식). `db @ host`는 DSN `user@host`와 충돌하는 비표준
- 환경 종속 요소(dev 전용 게이트·운영도구)는 코어 도식에서 빼고 **제외 사유를 비고에 명시**

## 사실 검증

- 포트·도메인·연결은 설정 원본(compose·게이트웨이 설정·IaC)에서 실측한 값만 적는다
- 다른 시스템 내부 경로는 그쪽 소스/설정으로 증명되는 것만 표기하고, 문서에 그 기준을 주석으로 남긴다
