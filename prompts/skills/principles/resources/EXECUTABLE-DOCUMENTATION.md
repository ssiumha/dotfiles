# EXECUTABLE-DOCUMENTATION — 실행되는 문서

## 정의

**문서가 노후하는 이유는 문서가 실행되지 않기 때문이다.** 코드는 틀리면 깨지지만 문서는 틀려도 조용하다. 그래서 시간이 지나면 팀은 문서를 믿지 않고 코드를 읽는다.

해법은 문서를 더 열심히 쓰는 것이 아니라, **문서를 CI가 실행하는 형태로 바꾸는 것**이다. 실행되면 틀린 순간 빌드가 실패하므로 드리프트가 구조적으로 불가능해진다.

```
설명하는 문서   →  틀려도 조용함  →  아무도 안 믿음  →  실질 가치 0
실행되는 문서   →  틀리면 빨간불  →  항상 최신       →  단일 진실 (SSoT)
```

[[SELF-DOCUMENTING-CODE]]가 "코드로 표현 가능한 것을 문서로 미루지 마라"라면, 이 원칙은 **"그래도 문서로 남겨야 하는 것은 실행 가능한 형태로 남겨라"**이다.

## 세 가지 실행 형태

| 형태 | 무엇을 고정하는가 | 수단 |
|------|------------------|------|
| **실행되는 예제** | 이 API를 어떻게 쓰는가 | doctest, README 코드블록 테스트 |
| **실행되는 구조 규칙** | 모듈 경계·의존 방향은 어떠한가 | fitness function (아키텍처 테스트) |
| **생성된 명세** | 인터페이스 계약이 무엇인가 | 코드 → OpenAPI/JSON Schema 자동 생성 |

세 형태 모두 같은 성질을 가진다 — **사람이 갱신하지 않아도 코드가 바뀌면 함께 바뀌거나 깨진다.**

### 1. 실행되는 예제

README와 docstring의 코드블록을 테스트로 실행한다.

| 언어 | 수단 |
|------|------|
| Rust | 내장 doctest (`cargo test`가 문서 예제를 컴파일·실행), README는 rust-skeptic |
| Python | 표준 `doctest`, `pytest --doctest-modules`, markdown은 pytest-codeblocks·mktestdocs·phmdoctest |
| Go | `Example` 함수 — `go test`가 실행하고 godoc이 문서로 표시 |
| Elixir | `doctest/1` — 모듈 문서의 iex 예제를 ExUnit이 실행 |
| TS/JS | 전용 도구가 유동적 — 도입 시점에 현재 유지보수되는 것을 확인 후 선택 |

핵심 조건: **테스트 명령에 포함되어야 한다.** 별도 명령으로 분리하면 아무도 안 돌리므로 실행되는 문서가 아니다 ([[SELF-TESTING-CODE]] 5조건).

### 2. 실행되는 구조 규칙 (fitness function)

아키텍처 다이어그램은 그려진 순간부터 낡는다. 계층·순환·경계 규칙을 테스트로 표현하면 위반이 머지되기 전에 차단된다.

규칙 유형·안티패턴·언어별 도구 감지표는 중복 작성하지 않는다 — `harness-engineering` 스킬의 `resources/06-arch-test-tools.md` 참조.

요약하면: 검증 대상은 **모듈 간 경계**이지 모듈 내부 구현이 아니다. 내부 구조까지 강제하면 리팩토링마다 테스트가 깨진다.

### 3. 생성된 명세

명세와 코드가 각각 손으로 관리되면 반드시 어긋난다. **생성 방향을 코드 → 문서 한쪽으로 고정**한다.

| 산출물 | 생성 원천 |
|--------|----------|
| OpenAPI 스펙 | 라우터·핸들러 타입 |
| JSON Schema | 도메인 타입 / 파싱 스키마 ([[PARSE-DONT-VALIDATE]]) |
| CLI 레퍼런스 | 명령 정의 (`--help` 출력을 문서에 주입) |
| ERD·의존 그래프 | 마이그레이션·import 그래프 |

수기 편집이 필요하면 그건 생성물이 아니라 또 하나의 진실 원천이다 ([[SSoT]] 위반).

## 핵심 판단

- **"이 문서가 틀리면 무엇이 깨지는가?"** — 아무것도 안 깨지면 실행되는 문서가 아니다
- **"이 규약을 어기면 CI가 잡는가, 리뷰어가 잡는가?"** — 사람이 잡으면 언젠가 놓친다
- **"README의 이 예제를 지금 복사해 실행하면 동작하는가?"** — 아무도 모른다면 이미 노후 중
- **"명세와 코드 중 어느 쪽이 원천인가?"** — 답이 "둘 다"면 드리프트는 시간 문제

## 위반 신호

### 기계적 검증 (자동화 가능)

| 신호 | 검증 방법 |
|------|-----------|
| 문서 코드블록이 테스트에 미포함 | 테스트 명령에 doctest/codeblock 러너 부재 |
| README 예제의 함수·인자가 코드에 없음 | 문서 심볼 grep → 코드 심볼 대조 (0건이면 노후) |
| 아키텍처 테스트 부재 | `06-arch-test-tools.md`의 언어별 도구 감지 절차 |
| 명세 파일이 수기 커밋됨 | `openapi.yaml` 등이 생성 스크립트 없이 직접 수정된 이력 (`git log`) |
| 문서 최종 수정일과 코드 최종 수정일 격차 | 같은 모듈의 doc vs src `git log -1 --format=%cr` 비교 |
| 주석 처리된 예제 코드 | 실행 안 되는 예제가 주석으로만 존재 |

### 판단 필요 (사람/LLM)

| 신호 | 설명 |
|------|------|
| "문서는 참고만 하세요, 코드가 최신입니다" | 문서가 이미 신뢰를 잃음 |
| 온보딩 때마다 문서대로 안 되는 단계가 나옴 | 셋업 문서가 실행되지 않음 |
| 같은 규약이 문서와 lint 규칙에 따로 존재 | 한쪽이 낡을 때까지 아무도 모름 |
| 아키텍처 다이어그램과 실제 import 방향 불일치 | 그림이 강제력을 갖지 못함 |
| PR 리뷰 코멘트가 매번 같은 규약을 반복 지적 | 사람이 lint 역할을 대신하는 중 |

## 스코어링

| 등급 | 기준 |
|------|------|
| **PASS** | 문서 코드블록이 테스트 명령에 포함, 구조 규칙이 CI 테스트로 존재, 명세가 코드에서 생성, 수기 문서는 WHY·의사결정만 |
| **WARN** | 예제는 실행되나 구조 규칙은 문서로만 존재 (또는 그 반대), 생성 명세 일부가 수기 편집 |
| **FAIL** | 문서 코드블록이 실행되지 않음 AND 구조 규칙이 강제되지 않음, 또는 문서와 코드가 각각 진실 원천 |

## 개선 패턴

| 상황 | 적용 |
|------|------|
| README 예제가 낡음 | **코드블록을 테스트로 실행** — 언어별 doctest 러너를 테스트 명령에 추가 |
| 사용법이 문서에만 있음 | **테스트를 사용 예제로 승격** — 테스트 이름을 시나리오 문장으로 ([[DAMP]]) |
| 아키텍처 규칙이 다이어그램에만 | **fitness function 도입** — 계층·순환·경계부터. 기존 위반은 freeze 후 점진 해소 |
| 명세와 코드 이중 관리 | **생성 방향을 코드 → 명세로 고정**, 생성물은 CI에서 diff 검사 |
| 규약이 문서와 리뷰 코멘트에 반복 | **lint 규칙으로 이동** — 위반 시점에 기계가 지적 |
| 셋업 문서대로 안 됨 | **셋업을 스크립트로** — 문서는 스크립트를 가리키기만 (`just setup`) |
| 제약이 문서에만 존재 | **타입으로 이동** ([[PARSE-DONT-VALIDATE]]) — 가장 이른 층위에서 잡힘 |

## 어디까지 실행 가능하게 만들 수 있나

```
타입          컴파일마다 검사       ← 가장 이른 피드백
  ↓
테스트·예제    커밋마다 실행
  ↓
fitness fn    머지 전 차단
  ↓
생성 명세      빌드마다 재생성
─────────────────────────────
WHY·의사결정·외부 제약·온보딩 맥락  ← 여기만 수기 문서로 남는다
```

수기 문서를 없애자는 것이 아니라, **위 네 층위로 내려보낼 수 있는 것을 문서에 남겨두지 말자**는 것이다. 남는 문서는 적어지고, 적어진 만큼 갱신된다.

## 다른 원칙과의 관계

| 원칙 | 관계 |
|------|------|
| [[SELF-DOCUMENTING-CODE]] | 그 원칙은 "코드로 표현 가능한 것을 문서로 미루지 마라", 이 원칙은 "남은 문서는 실행 가능하게" |
| [[SELF-TESTING-CODE]] | 실행되는 문서는 빌드에 묶여야 성립 — 5조건이 그대로 적용된다 |
| [[SSoT]] | 명세·문서·코드가 각각 진실이면 드리프트. 생성 방향을 한쪽으로 고정하는 근거 |
| [[PARSE-DONT-VALIDATE]] | 타입 층위의 실행되는 문서 — 컴파일러가 검사하는 계약 |
| [[COMMENT-WHY]] | 실행 불가능한 영역(WHY)만 주석·문서로 남긴다는 경계선 |
| [[BEYONCE-RULE]] | "중요하면 테스트로 보호하라"를 문서·구조 규칙까지 확장 |
| [[DAMP]] | 테스트가 문서 역할을 하려면 읽어서 이해되는 이름·구조여야 |
| [[CHESTERTONS-FENCE]] | 실행되는 규칙은 "왜 있는지"를 깨뜨려 봄으로써 알려준다 |
| [[BROKEN-WINDOWS]] | 노후한 문서를 방치하면 전체 문서 신뢰가 무너진다 |

## 잘못된 통념 교정

| 통념 | 실제 |
|------|------|
| "문서화를 잘하면 드리프트가 준다" | 갱신 규율은 반드시 느슨해진다. 실행되게 만드는 것이 유일하게 지속 가능 |
| "doctest는 장난감 예제용" | 공개 API 사용법 고정에는 충분하다. 복잡한 검증은 일반 테스트가 맡으면 된다 |
| "아키텍처 테스트는 대규모 팀 전용" | 계층 규칙 3~4개로 시작할 수 있다. 도메인 모델이 없는 초기에도 선적용 가능 |
| "생성된 문서는 읽기 나쁘다" | 생성물에 수기 서술을 덧붙이면 된다. 계약 부분만 생성 대상 |

## 주의

- **모든 문서를 실행 가능하게 만들 수는 없다.** 의사결정 기록(ADR), 아키텍처 개요, 규제·외부 계약, 온보딩 맥락은 계속 수기 문서다
- 문서 예제를 테스트로 돌리면 문서가 테스트 제약(빠름·결정적)을 받는다. 느린 예제는 별도 통합 테스트로 분리
- fitness function을 너무 세밀하게 걸면 리팩토링마다 깨진다 — 경계만 검증
- 생성 명세를 CI에서 검사하려면 생성 결과가 결정적이어야 한다 ([[IDEMPOTENCY]]). 순서·타임스탬프가 섞이면 매번 diff가 난다
- 레거시에 한 번에 적용하지 않는다. 새로 만지는 영역부터 ([[BOY-SCOUT]])
